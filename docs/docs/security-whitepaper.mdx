# AliasVault Security Whitepaper

**Security architecture, cryptographic design and threat model**

*Version 0.5, 2026-10-22. See [Document information](#document-information).*

This document describes how AliasVault protects user data: which keys exist, where they are created and stored, how clients authenticate, how personal vaults, shared vaults and emails are encrypted, and what the server can and cannot do. It covers the cryptographic design of all clients and the server, the threat model and the known limitations. It does not cover the operational security of AliasVault Cloud or any other deployment, or the security of the platforms the clients run on. The source code is the final reference and is linked from [Appendix A](#appendix-a-implementation-map).

## 1. Architecture overview

AliasVault is a password and email alias manager with end-to-end encryption. It stores credentials, passkeys, TOTP secrets, notes, identities and attachments in a vault that is encrypted on the user's device, and it runs its own email server so that every alias address receives mail that is stored encrypted for the vault the alias belongs to. It consists of:

- **Server**: a .NET API, an admin portal, an SMTP service and a task runner, backed by PostgreSQL. The server stores encrypted vaults and emails, routes mail to aliases, authenticates users and keeps the metadata needed to do so.
- **Clients**: a web app, browser extensions (Chrome, Firefox, Edge, Safari) and native iOS and Android apps.
- **Rust core**: one library, compiled to WebAssembly for the web app and browser extensions, and to native libraries for iOS and Android. This core implements key derivation, key encryption, signing, SRP, the vault format, sync and merge, passkeys and the email parser. Every client runs the same cryptographic code.

All of it is open source under the AGPL-3.0 license in one repository: [github.com/aliasvault/aliasvault](https://github.com/aliasvault/aliasvault). The same code runs as AliasVault Cloud ([app.aliasvault.com](https://app.aliasvault.com)), operated by the AliasVault team, and as self-hosted instances. In this document "the server" means whichever of the two a user's clients talk to, and "the server operator" means the party running it; the threat model treats the server as untrusted in both cases.

"Zero-knowledge" is used in one sense: the server never holds a key that decrypts a vault, and never receives vault contents in a form it can read. Vault contents are encrypted on the device before upload, incoming email is encrypted on arrival with the public key of the vault its alias belongs to, and a shared vault's key is stored only encrypted for each member's public key. Three things fall outside this definition. The server handles each incoming email in plaintext for the moment it takes to encrypt it, and it delivers the web app's code (both in [2.2](#22-trust-assumptions)). It also keeps the metadata it needs to route mail and serve accounts ([2.4](#24-what-the-server-knows-and-can-do)).

## 2. Threat model

This section states what AliasVault protects, against whom, and under which assumptions. Each guarantee holds against a server that deviates arbitrarily from its expected behaviour ([2.3](#23-threat-actors)), except where [section 13](#13-known-limitations) says otherwise.

### 2.1. Assets
In order of value:

1. The master password and the keys derived from it (the unlock key and the KEK).
2. The Account Key, the Vault Encryption Keys, the account private keys and the vault delivery private keys.
3. Vault contents: credentials, passkey private keys, TOTP secrets, notes, identities and attachments.
4. The contents of emails received on aliases.
5. API session tokens. They give access to encrypted data and to account actions, not to decryption.
6. Metadata: usernames, alias addresses and the vault each belongs to, sharing relationships, vault sizes and change times, and authentication logs.

### 2.2. Trust assumptions
The guarantees in this document hold under the following assumptions.

- **The device and its operating system are trusted.** Everything AliasVault decrypts exists on the device while the vault is unlocked, so malware running with the user's privileges, a rooted or jailbroken device with hostile tooling, a keylogger, or an attacker reading process memory sees what the user sees. AliasVault hardens against this where the platform allows ([section 11](#11-protecting-keys-on-the-device)), but data on a compromised device is outside what it can protect. Locking the vault removes the decrypted vault and the keys from memory, so a device compromised after locking yields ciphertext only; in JavaScript hosts, memory clearing is best effort.
- **The client code is authentic.** The user runs an unmodified AliasVault client obtained from an official channel. The browser extensions and the mobile apps are installed once, from the extension stores, the app stores, F-Droid, the GitHub releases or the official downloads website (downloads.aliasvault.com), and do not load code from the server, so a server that later turns malicious cannot change them. The web app, like every web application, loads its code from the server, which lets you reach your vault from any browser without installing software. For the web app, the server and the TLS connection are therefore trusted to deliver the published code; the browser extension and the mobile apps do not depend on this.
- **The master password is strong and secret.** Anyone holding a copy of the user's encrypted data (the server database, device storage, an export) can run an offline guessing attack at the cost of one Argon2id derivation per guess, and there is no second secret mixed into the derivation. AliasVault requires at least 12 characters and shows a strength indicator, but the strength of the password is the user's choice.
- **The standard cryptography is sound.** Argon2id, AES-256-GCM, RSA-OAEP, Ed25519, SRP-6a, HKDF and HMAC with SHA-256, and the platform's random number generator (WebCrypto in browsers, the system generator on iOS and Android).
- **Members of a shared vault are trusted with that vault.** A member can read and copy everything in the vault. Removing a member stops their future access through the server; it cannot take back what they already synced ([13.1](#limitation-shared-member-removal)).
- **Account fingerprints are exchanged outside AliasVault.** A client accepts another user's key only when its fingerprint is the account fingerprint its user typed ([10.3](#103-account-fingerprints-and-key-certifications)). This protects against a substituted key only when the fingerprint came from that person over a channel the server does not control.
- **TLS protects the transport, but vault confidentiality does not depend on it.** The master password never crosses the wire (SRP), and vault data is encrypted before it is sent. A broken TLS connection exposes session tokens and metadata, which could give API access but no decryption. The mobile apps only connect over `https://` and do not pin certificates: any certificate the device trusts is accepted, including a certificate authority the user installed, so that self-hosted servers with a private certificate authority work.
- **The server operator is trusted at the moment an email arrives.** Email reaches the SMTP service in plaintext, as the protocol requires, and is encrypted in memory before it is stored. Email encryption therefore protects stored email against later access to the database, backups and the API, not against an operator who captures mail as it arrives. Transport from the sender to the SMTP service depends on the sender's use of STARTTLS, which the service offers when certificates are configured.

### 2.3. Threat actors
The last column names the mechanism and the section that describes it.

| Adversary | Assumed capabilities | Must not be able to | Mechanism |
|---|---|---|---|
| **Malicious or compromised server** (operator, insider, intruder, leaked database or backups) | Reads and modifies everything the server stores; controls every API response; serves any public key, setting or version it likes | Read vault or stored email contents; learn the master password or any key; forge or alter vault contents undetected; move data between vaults, fields or users; make a client derive a key below the client-enforced minimum | Client-held key hierarchy ([4](#4-key-derivation-and-key-hierarchy)); AES-256-GCM bound to its slot ([4.1](#41-key-hierarchy), [6](#6-vault-operations)); other users' keys accepted only against their out-of-band provided account fingerprint, grants opened only when signed by the account itself ([10.3](#103-account-fingerprints-and-key-certifications)); client-side Argon2id minimum ([4](#4-key-derivation-and-key-hierarchy)); known limitations: rollback ([13.2](#limitation-rollback)), email on arrival ([2.2](#22-trust-assumptions)) |
| **Network attacker** (on-path, rogue access point, mis-issued certificate) | Reads and modifies traffic between client and server | Learn the password or any key; read vault contents; impersonate the server to a client during login | SRP with mutual proof ([5](#5-authentication-process)); vault data encrypted before transmission ([6](#6-vault-operations)); TLS |
| **Malicious website** visited while the extension is installed | Runs scripts in its own page, sends messages to the content script, calls the WebAuthn API | Obtain credentials or passkey signatures for another site; trigger autofill for another origin; read extension storage | Autofill suggestions matched on the registrable domain; one item released per user pick, only to the frame it was picked in; content-script isolation; WebAuthn origin and relying-party checks ([8](#8-passkey-authentication)) |
| **Another AliasVault user**, including current and former shared-vault members | Holds their own account, grants they were given, and copies of data they synced | Open a vault they were not invited to; read another user's personal vault; keep receiving a shared vault's mail after removal | One VEK per vault, grants only to invited accounts, per-vault authorization on the server for vaults and their email ([10](#10-vault-sharing)) |
| **Holder of a stolen session token** | Calls the API as the user until the token expires or its session is revoked | Decrypt anything; send an alias's future email to another vault; approve a Login with Mobile request | Tokens never decrypt; access tokens live 10 minutes; refresh tokens are stored hashed and rotated on use ([5.3](#53-session-tokens)); Login with Mobile approvals are signed and refused from a revoked session ([9.2](#92-login-flow)); alias moves are signed ([7.1](#71-key-generation-and-storage)) |
| **Holder of a copy of the encrypted data** (server database, device storage, backup, export file) | Unlimited offline computation | Decrypt without the master password or export password | Argon2id with a client-enforced minimum ([4](#4-key-derivation-and-key-hierarchy), [12](#12-vault-exports)); known limitation: the opt-in extension PIN can be guessed offline from a copy of the extension storage ([13.3](#limitation-pin-unlock)) |
| **Sender of a crafted email** | Sends any content to any alias | Run code in a client; read anything from the vault; learn anything about the recipient | Parser in the memory-safe Rust core; HTML sanitized and rendered in a sandboxed frame without scripts; attachments never opened automatically ([7](#7-email)) |
| **Person with physical access to a locked device** | Uses the device as found | Unlock without the master password, PIN or biometrics | Device unlock methods with attempt limits ([11](#11-protecting-keys-on-the-device)); anything beyond that is out of scope ([2.5](#25-out-of-scope)) |

### 2.4. What the server knows and can do
**Stored in plaintext on the server:**

- Account: username, creation and last-activity times, the SRP salt and verifier, the Argon2id settings of each account unlock method, the TOTP secret and recovery codes when two-factor authentication is enabled, and lockout and block state.
- Keys: public keys with their signatures; every private and symmetric key only in encrypted form ([4.1](#41-key-hierarchy)).
- Vaults: the ciphertext of manifests, data buckets and blobs, with manifest ids, revision numbers, sizes, upload times, ciphertext hashes and a limited history of older versions; the number of items in each vault, reported by the client for operational statistics; and the blobs each vault revision references, with their kind (attachment or logo).
- Sharing: groups, their members and roles, which accounts hold a grant on which vault, pending invitations, and key certifications (which account verified which other account's signing key).
- Aliases: every alias address, the vault it belongs to, its state (active, paused, removed) and its creation time.
- Email: the recipient alias, the time received, the sender's `Date` header, the attachment count and the ciphertext size ([7.4](#74-what-the-server-sees)).
- Logos: the URL of an item whose logo is fetched through the server's favicon service.
- Activity: an authentication log with the IP address, a country derived from it, device type, operating system, browser, time and outcome of every login attempt and security-relevant action; the pending Login with Mobile requests ([9](#9-login-with-mobile)).

**What the server can do:**

- Deny service, delete data and block accounts ([2.5](#25-out-of-scope)), and serve an older version of a vault ([13.2](#limitation-rollback)).
- Through the admin portal: see the metadata above, disable a user's two-factor authentication, change a username, change or remove a user's aliases, and block or delete an account. Within 7 days by default, it can also undo a password change made without a key rotation ([4.1](#41-key-hierarchy)).
- Serve modified web app code ([2.2](#22-trust-assumptions)).
- Read an incoming email at the moment it arrives ([2.2](#22-trust-assumptions)), and deliver an email of its own making to any alias.
- Answer whether an alias address is taken, which anyone can also learn from the SMTP bounce for an unknown address.

**What the server cannot do:**

- Read vault contents or stored email contents, or learn the master password, the unlock key, the KEK, the Account Key, any VEK, any blob key or any private key.
- Check a guess of the master password cheaper than one Argon2id derivation per guess: the SRP verifier and the encrypted Account Key cost the same, and the SRP input cannot be turned into the KEK.
- Modify vault contents, or move ciphertext between vaults, data buckets, blobs or users, without the client refusing it.
- Give anyone access to a vault: only a holder of the VEK can create a grant, and a client opens a shared vault only with a grant it signed itself.
- Pass a key of its own off as another user's: a client accepts another user's signing key only when its fingerprint is the account fingerprint its user typed, and its own account public key only when it belongs to the private key it holds ([10.3](#103-account-fingerprints-and-key-certifications)).
- Learn passkey private keys or TOTP secrets stored in a vault, or produce passkey signatures.

### 2.5. Out of scope
AliasVault does not defend against the following, and reports that depend on them are classified as hardening, not as security boundary failures (see [SECURITY.md](https://github.com/aliasvault/aliasvault/blob/main/SECURITY.md)):

- A compromised device: malware with the user's privileges, rooted or jailbroken devices with hostile tooling, kernel-level or runtime instrumentation, malicious accessibility services, memory dumps of a running client, and forensic extraction of device storage or backups.
- A weak, reused or disclosed master password.
- Social engineering where the app accurately presents the action and the user approves it.
- Tampered client builds and compromise of the channels that deliver them (extension and app stores, F-Droid, GitHub, the user's browser), and vulnerabilities in the operating system, browser or hardware.
- Availability. A malicious server can always refuse to serve or delete data; local copies and exports are the mitigation.
- Hiding whether a username is registered. On a server with public registration, registration and the username availability check reveal it, rate limited per IP address. When registration requires an invite code, both require a valid code, and the login endpoint answers an unknown username with a substitute SRP response that stays the same across requests; a locked or blocked account still answers with its own error.
- Side channels on the device, and traffic analysis beyond the metadata listed in [2.4](#24-what-the-server-knows-and-can-do).

## 4. Key derivation and key hierarchy
Your master password never leaves your device. It unlocks your Account Key, the key that opens all your vaults and that the server only ever stores in encrypted form. When you log in, it is also used to calculate a proof the server can check without knowing the password itself.

- Your master password is processed with Argon2id (a memory-hard key derivation function) on your device
    - Argon2id parameters used for the master password: 64 MiB memory, 5 iterations, parallelism 1, salt = the account's random 32-byte SRP salt (created on the client at registration and stored on the server)
    - The server sends the salt and the account's settings at login. The client refuses settings below a fixed minimum built into the Rust core (19 MiB, 2 iterations, parallelism 1, the parameters of the first public release), and a device that has logged in before also refuses settings weaker than those it used previously. Older accounts that still use weaker settings are upgraded to the current defaults (64 MiB, 5 iterations) the next time the user logs in with their master password. The password and salt stay the same. The server never stores settings below the current defaults, so the upgrade can only make the settings stronger.
- The derived key is the unlock key. It is never used as-is; two keys are derived from it with HKDF-SHA256, each under its own label:
    - The SRP input (label `AliasVault SRP v1`), for authentication with the server through the SRP protocol
    - The Key Encryption Key (KEK, label `AliasVault KEK v1`), which decrypts the Account Key
- The SRP input and the KEK are independent: neither can be calculated from the other, or back to the unlock key and the master password. Even if the value used for login were exposed (e.g. in logs), it would not reveal the key that decrypts the Account Key.

### 4.1. Key hierarchy
Every unlock method (e.g. master password) opens the same Account Key, which unlocks a chain of random keys, all created on the client. Each vault has its own key, so giving a user access to a shared vault does not give them access to your personal vault or to other shared vaults:

| Key | What it is | What it protects | Stored on the server as |
|---|---|---|---|
| **KEK** (Key Encryption Key) | Derived from an account unlock method; for the master password, with HKDF-SHA256 from the unlock key (its Argon2id output) | The Account Key | Never stored |
| **AK** (Account Key) | Random 256-bit key, created at registration | The personal VEK and the private keys of both account keypairs | Encrypted with the KEK, one copy per account unlock method |
| **VEK** (Vault Encryption Key) | Random 256-bit key, one per vault: the personal vault and any shared vaults have separate keys | The vault contents and its blob keys | Encrypted with the owner's AK (personal vault) or with each member's account public key (shared vault) |
| **Account encryption keypair** | RSA-2048 keypair, one per user | Private key opens the VEKs of shared vaults this user is a member of | Public key in plaintext (signed with the user's account signing key), private key encrypted with the AK |
| **Account signing keypair** | Ed25519 keypair, one per user | Signs what the user publishes or changes on the server, such as their RSA public key and grants | Public key in plaintext, private key encrypted with the AK |
| **Vault Delivery Keypair** | RSA-2048 keypair, one per vault | Private key opens emails for aliases in that vault | Public key in plaintext, private key stored inside the encrypted vault |
| **Blob key** | Random 256-bit key, one per blob (content stored separately from the rest of the vault, such as the bytes of an attachment or logo) | That blob's bytes | Encrypted with the VEK of the vault the blob belongs to |

**Key vs keypair:** a *key* is a single secret used to encrypt and decrypt (AES-256-GCM). A *keypair* has a public key that can be shared openly to encrypt or verify, and a private key that decrypts or signs and is only stored encrypted.

All symmetric encryption in this chain uses AES-256-GCM, all asymmetric encryption uses RSA-OAEP with SHA-256. Every ciphertext is bound to its place with AES-256-GCM associated data or an RSA-OAEP label ([`aad.rs`](https://github.com/aliasvault/aliasvault/blob/main/core/rust/src/crypto/aad.rs)), so a ciphertext taken from one slot does not decrypt in another and a vault served under another vault's id is refused.

Properties of this hierarchy:
- **Device unlock methods** (biometrics, PIN, passkey quick unlock) keep their own encrypted copy of the Account Key on the device only, protected by the device keychain, a PIN-derived key or a passkey PRF key, never the password-derived keys. Login with Mobile hands the Account Key over once, encrypted with a one-time RSA key. They keep working after a password change and are set up again after a key rotation. Every unlock walks the same chain from the Account Key down, so all keys below it always become available together.
- **Additional account unlock methods** can be enabled by encrypting the same Account Key with another KEK, without having to re-encrypt the vault or invalidating existing unlock methods.
- **Password change** gives the user two options:
    - **1) Change the password (default)**: only the Account Key (AK) is encrypted again, with the new KEK. Vault contents, attachments and shared vault access stay unchanged, so nothing has to be re-encrypted or uploaded. The user's other devices are signed out and log in again with the new password; device unlock methods keep working. This is a small, quick change and is sufficient in most cases.
        - **Undoing a password change**: a user who is locked out because they did not save their new password can ask an administrator to restore their old one, within 7 days of the change. For this, the server keeps the previous encrypted Account Key for that period. Only the old password decrypts it, so after a revert only someone who knows that password can log in with it. The administrator cannot decrypt it, log in with it or read the vault, and until a revert it is not sent to any client. A revert signs out all sessions and is logged. The server operator sets the retention period (0 turns it off); a password change with key rotation removes any remaining password history.
    - **2) Change the password and rotate all keys** (opt-in, [4.2](#42-key-rotation)): also replaces the Account Key and the keys below it, and re-encrypts the personal vault. This is needed when the old password or the keys may have been exposed, for example on a compromised or stolen device: a normal password change does not lock out someone who already used the old password, as they hold the Account Key and it stays the same. A rotation cannot be undone, and changes on another device that were not yet synced are lost. Before it starts, the client asks the user to export a backup of the vault, let their other devices finish syncing and sign out from them, and to confirm they did so. Afterwards, device unlock methods have to be set up again.

### 4.2. Key rotation
When you change your master password, you can choose to also replace all encryption keys of your account. Without it, a password change keeps the keys ([4.1](#41-key-hierarchy)).

- **Replaced**: the Account Key, the personal VEK, both account keypairs and the personal vault's Vault Delivery Keypair, all created on the client.
- **Re-encrypted**: the personal vault and its blob keys with the new VEK, and every grant the user holds for the new account public key.
- **Signed again**: every key certification the user made, with the new signing key, after the client verified it under the old one ([10.3](#103-account-fingerprints-and-key-certifications)).
- **Unchanged**: blob bytes, shared vault VEKs and received emails, whose old delivery keypair stays in the vault.
- **Deleted**: the previous personal VEK, the older revisions of the personal vault with the blobs only they refer to, the password history and the old account encryption keypair, as they can only be opened with the old keys. The old signing public keys stay on the server.
- **All or nothing**: the server applies the rotation in one transaction and refuses it when a blob key or grant is missing or the vault changed in the meantime.
- **Other devices**: their sessions are revoked, and a device still on the old keys is signed out on its next sync. Device unlock methods have to be set up again, and pending invitations to the user are closed.
- **Scope**: the old keys cannot decrypt anything written to the personal vault after the rotation. Received emails and shared vaults stay under their existing keys ([13.1](#limitation-shared-member-removal)).

## 5. Authentication process
Your master password is never sent to the server. Instead, during login, client and server authenticate each other with the SRP protocol: the client proves it holds the key derived from your password, and the server proves it holds the matching verifier, without either side sending its secret. When two-factor authentication is enabled, the server also checks a TOTP code before it issues API session tokens. These tokens give access to your account on the server, but can never decrypt your vaults.

### 5.1. SRP login
- SRP-6a with the 2048-bit group of RFC 5054 and SHA-256; the password itself is never sent
- The SRP identity is a random per-account id, so a username change does not change the verifier
- Client and server each prove they derived the same session key; the client checks the server's proof before accepting any token

### 5.2. Two-factor authentication
- Optional: when enabled, a TOTP code from a standard authenticator app is required after the SRP step
- The server only issues session tokens after the code is verified
- Two-factor authentication protects access to the account on the server. It is not part of the encryption: the TOTP secret and the recovery codes are stored on the server, and a vault is still protected by the master password alone

### 5.3. Session tokens
- A short-lived JWT access token (10 minutes, signed with HMAC-SHA256) and a refresh token (8 hours by default, 14 days when the user chooses to stay logged in; both configurable by the server operator). The refresh token is stored hashed on the server, so a database leak does not expose usable tokens, and is rotated on every use, so a copied refresh token stops working once the legitimate client refreshes
- Tokens grant API access only; they never decrypt anything
- The user can see their active sessions and authentication log in the security settings of the clients and revoke any session

### 5.4. Brute-force protection
- After 10 failed login attempts an account is locked for 30 minutes
- Registration, Login with Mobile, logo fetching and alias availability checks are rate limited per account and per IP address, and the server operator can block IP ranges
- Every login attempt and security-relevant action (password change, key rotation, two-factor changes, logout, shared vault creation, deletion, invitations, joins, leaves and access revocations, key certifications, account deletion) is written to the authentication log with the IP address and client details

## 6. Vault operations
Your vaults are always encrypted on your device before they are uploaded. Each vault (your personal vault and every shared vault) is stored on the server as one encrypted *manifest*, plus separate data buckets and blobs. The server only receives and stores these in encrypted form and can never read their contents.

<a href={useBaseUrl('/assets/diagrams/whitepaper/6-vault-operations.html')} target="_blank" rel="noopener noreferrer" title="Open full screen">
  <ThemedImage
    alt="AliasVault vault storage format diagram"
    sources={{
      light: useBaseUrl('/assets/diagrams/whitepaper/6-vault-operations-light.svg'),
      dark: useBaseUrl('/assets/diagrams/whitepaper/6-vault-operations-dark.svg'),
    }}
  />
</a>

- Vault contents are encrypted and decrypted on the device with AES-256-GCM and only reach the server encrypted
- The encryption key is the vault's VEK (see [Key hierarchy](#41-key-hierarchy)), not the master password itself
- Each manifest is encrypted with the VEK of its vault and bound to its manifest id, so the server cannot swap one vault's data for another's. Data that changes often, such as UI settings and usage statistics, is kept in separate *data buckets* that sync on their own, so a small change like a different sort order does not require uploading all items again; how a vault is split into manifests, data buckets and blobs is described in [Vault Format and Sync](./security-architecture/vault-format.mdx#the-storage-format).
- Some content, such as the bytes of attachments and logos, is stored outside the manifest as separate blobs, each encrypted with its own random blob key; the blob key is encrypted with the VEK of the vault the blob belongs to. A blob is addressed by `HMAC-SHA256(manifest salt, plaintext)`, where the manifest salt is a random value that lives inside the encrypted manifest, so the server cannot recognize the same file across vaults while every member of a shared vault computes the same address
- On the device, the vault is only decrypted in memory while it is unlocked. The copy kept on disk stays encrypted with the VEK, together with the encrypted key hierarchy, so a device can unlock offline
- The server keeps a limited number of older versions of each manifest and data bucket as a backup against potential client-side data corruption; a key rotation deletes the personal vault's older versions ([4.2](#42-key-rotation)). Blobs never change; a blob is deleted once no kept version refers to it anymore

## 7. Email
AliasVault encrypts each incoming email in memory as soon as it arrives, with the delivery public key of the vault the alias belongs to, and only writes its content to the database in encrypted form. Only people with access to that vault hold the private key and can read its emails.

    alt="AliasVault email encryption diagram"

    }}

### 7.1. Key generation and storage
1. Every vault (personal or shared) has its own Vault Delivery Keypair (RSA-2048), generated locally on the client
    - The private key is stored inside that encrypted vault
    - The public key is sent to the server together with the vault, signed with the publishing user's account signing key; the server only accepts a key signed by a member allowed to publish it
2. Each alias is registered on the server as an *email claim*, which links the alias to the vault it belongs to
    - Moving an alias to another vault is signed with the user's account signing key, over the alias, both vaults and the current version of the claim; the server only accepts a move signed by the caller, so a stolen session token alone cannot send an alias's future email to another vault

### 7.2. Email reception process
1. When an email is received, the server:
    - Checks whether the recipient address matches an active email claim
        - If there is none, the email is rejected
    - Generates a random 256-bit symmetric key
    - Encrypts the email content (subject, sender fields, bodies, preview, raw source and attachments) using this symmetric key with AES-256-GCM
    - Encrypts the symmetric key with the delivery public key of the vault the claim belongs to (RSA-OAEP)
    - Stores the encrypted email and the encrypted symmetric key

### 7.3. Email retrieval process
1. The client retrieves the encrypted email and the encrypted symmetric key
2. The client decrypts the symmetric key with the delivery private key of the matching vault
3. The client decrypts the email contents with the symmetric key
4. All decryption occurs locally on the client device
5. The email is parsed by the Rust core, its HTML is sanitized, and it is shown in a sandboxed frame that cannot run scripts

### 7.4. What the server sees
- Email is end-to-end encrypted from the moment it is stored, not from the sender: the SMTP service sees each message in plaintext while it encrypts it ([2.2](#22-trust-assumptions)). Transport from the sender is protected only if the sender uses STARTTLS
- The recipient alias, the time received, the sender's `Date` header, the attachment count and the ciphertext size stay in plaintext, so the server can list and expire mail without decrypting it. The alias-to-vault mapping is plaintext because the server needs it to route mail
- Email content is untrusted input. Anyone can send to an alias, so the encryption proves nothing about who wrote a message; the clients treat every email as hostile content

## 8. Passkey authentication
Your passkeys are stored in your vault and encrypted like the rest of its contents. AliasVault acts as the passkey authenticator (WebAuthn Level 2): it creates each passkey's keypair, keeps the private key in your vault, and only gives websites the public key and signatures. You can use your passkeys in every AliasVault app that supports them.

  <ThemedImage
    alt="AliasVault passkeys diagram"
    sources={{

      dark: useBaseUrl('/assets/diagrams/whitepaper/8-passkeys-dark.svg'),

### 8.1. Virtual authenticator implementation
- The authenticator logic (key generation, authenticator data, attestation, signatures and PRF) is implemented once in the Rust core and shared by every app
- Browser extension: intercepts `navigator.credentials` on the page and checks the website against the page's origin (Public Suffix List rule plus WebAuthn Related Origin Requests) before calling the core
- iOS: credential provider extension (AuthenticationServices) calling the core
- Android: Credential Manager provider service calling the core

### 8.2. Passkey registration process
When a website asks to create a passkey:
- The client creates a new keypair, ES256 (ECDSA P-256) or RS256 (RSA-2048), whichever comes first in the website's list of accepted algorithms
- The private key is saved as part of the vault, so it is encrypted and synced like any other vault content
- The website receives the public key in an attestation object with AliasVault's AAGUID (`a11a5faa-9f32-4b8c-8c5d-2f7d13e8c942`) and the flags UP (user present), AT (attested credential data), BE (backup eligible) and BS (backed up), plus UV when the user was verified
- The attestation format is "none" or "packed" self-attestation, and the sign count is always 0, as is usual for passkeys that sync between devices

### 8.3. Passkey authentication process
When a website asks to sign in with a passkey:
- The client takes the passkey from the unlocked vault and signs the website's challenge with its private key
- Only the signature is sent to the website; the private key never leaves the client

### 8.4. PRF extension
- Passkeys support the WebAuthn PRF extension (hmac-secret), which lets a website derive a stable secret from a passkey, for example to encrypt its own data
- When a website asks for PRF at registration, a random 32-byte secret is created and saved in the vault with the passkey; for each salt the website sends, the client returns `HMAC-SHA256(secret, SHA-256("WebAuthn PRF" || 0x00 || salt))`

## 9. Login with Mobile
You can log in to the web app or browser extension by scanning a QR code with the AliasVault mobile app, without typing your master password. The device you log in on creates a one-time keypair. The mobile app encrypts your Account Key with it and sends it to that device via the server, so only these two devices can read it.

<a href={useBaseUrl('/assets/diagrams/whitepaper/9-login-with-mobile.html')} target="_blank" rel="noopener noreferrer" title="Open full screen">
  <ThemedImage
    alt="AliasVault login with mobile diagram"
    sources={{
      light: useBaseUrl('/assets/diagrams/whitepaper/9-login-with-mobile-light.svg'),
      dark: useBaseUrl('/assets/diagrams/whitepaper/9-login-with-mobile-dark.svg'),
    }}

### 9.1. What passes through the server
Two pieces of data travel through the server, both encrypted for the one-time public key of the device you log in on:
- The Account Key, encrypted by your phone with RSA-OAEP
- The new session tokens and account details, encrypted by the server with a random AES-256-GCM key, which is itself encrypted with RSA-OAEP

### 9.2. Login flow

1. **Initiation (requesting client: web app or browser extension)**
   - Client generates a one-time RSA-2048 keypair locally, only for this login request
   - Public key is sent to the server
   - Server creates a unique request ID and a poll secret, stores the public key and only a hash of the poll secret
   - Client generates a QR code containing the request ID and a SHA-256 hash of the public key
   - Client shows a 2-digit verification code derived from the public key
   - The one-time private key only exists in memory for the duration of this login request: it is never stored on disk or in a vault

2. **QR code scan (mobile app)**
   - User scans the QR code with their authenticated mobile app
   - Mobile app retrieves the public key and requester details (browser, OS, IP address) from the server and checks the public key against the hash in the QR code
   - User picks the verification code shown on the requesting screen out of four options, approves, and confirms with biometrics or PIN
   - Mobile app encrypts the user's Account Key with the one-time public key generated by the requesting client (RSA-OAEP)
   - Encrypted Account Key is sent to server, signed with the user's account signing key
   - Server temporarily stores the encrypted Account Key and marks the request as fulfilled

3. **Polling and retrieval (requesting client)**
   - Client polls the server every few seconds with its poll secret
   - When fulfilled, server:
     - Creates a new session for the user: a JWT access token and refresh token that give the requesting client access to the API, similar to a password login (see [Authentication process](#5-authentication-process))
     - Creates a random 256-bit symmetric key
     - Encrypts the JWT tokens, username and the account's Argon2id settings with this symmetric key (AES-256-GCM)
     - Encrypts the symmetric key itself with the requesting client's one-time public key (RSA-OAEP)
     - Returns all encrypted data in the response
     - Immediately marks the request as retrieved and deletes the stored one-time public key and encrypted Account Key from the database

4. **Decryption (requesting client)**
   - Client decrypts the Account Key and the symmetric key with its one-time private key
   - Client decrypts the JWT tokens, username and Argon2id settings with the symmetric key
   - Client unlocks the rest of the key hierarchy with the Account Key, as with a password login
   - The one-time private key is discarded from memory

### 9.3. Request binding and lifetime
- **Bound to the requesting client**: the QR code holds a hash of the one-time public key, which the mobile app checks, so the server cannot swap in a key of its own. The verification code the user picks in the mobile app is derived from the same key, so a request started by someone else is not approved by accident.
- **Only the requesting client gets the result**: retrieving it requires a poll secret that the server hands only to the requesting client and stores only as a hash. Someone who sees the QR code or has a copy of the database therefore cannot retrieve it.
- **Short-lived and one-time**: a request must be approved within 3 minutes and retrieved within 1 minute after that, it can be retrieved only once, and expired requests are cleaned up by the server.
- **The user is the last check**: the mobile app shows the requester's client, operating system, IP address, location and the time the request was made, and warns with a delay when the request was opened from a link instead of the in-app scanner. Approving a request the user did not start hands the Account Key to whoever started it ([2.5](#25-out-of-scope)).

## 10. Vault sharing
You can create shared vaults and invite other people to them. In the apps, a shared vault is shown as a shared folder at the top level of your vault. A shared vault is separate from your personal vault and has its own VEK, so members never get access to your personal vault or your master password. Each member receives the shared vault's VEK encrypted for their own account, so the server only stores encrypted copies of it.

<a href={useBaseUrl('/assets/diagrams/whitepaper/10-vault-sharing.html')} target="_blank" rel="noopener noreferrer" title="Open full screen">
  <ThemedImage
    alt="AliasVault vault sharing diagram"
    sources={{
      light: useBaseUrl('/assets/diagrams/whitepaper/10-vault-sharing-light.svg'),
      dark: useBaseUrl('/assets/diagrams/whitepaper/10-vault-sharing-dark.svg'),
    }}
  />
</a>

Every shared vault has its own *group*, which manages the people it is shared with. The creator owns the group and invites people; the others are members.

Access to a shared vault is called a *grant*: a copy of the vault's VEK encrypted with one member's account public key, which only that member's account private key can decrypt. Every member, the creator included, has their own grant; the server stores the grants but cannot open them.

### 10.1. Sharing flow
1. **Creation**
   - A user creates the shared vault on their client; the server creates its group, owned by that user
   - The client generates a new VEK and a Vault Delivery Keypair for the vault
   - The admin's own grant is created: the VEK encrypted with the admin's account public key (RSA-OAEP), signed with the admin's account signing key. The client first checks that this public key belongs to the private key it holds
   - The vault name is encrypted with the VEK, so only members can read it; the server never sees the name of a shared vault

2. **Invitation**
   - The first time two people share, the owner types the account fingerprint the other person gave them outside AliasVault. The owner's client checks that the signing key the server returns for that account has this fingerprint, signs a key certification of it and stores it on the server ([10.3](#103-account-fingerprints-and-key-certifications)). Later invitations reuse this certification; without it the invitation is refused
   - The client accepts the invitee's account public key only when it is signed by the certified signing key. The shared VEK and the vault name are encrypted with that public key and signed by the owner, so the invitee can see which vault they are invited to before accepting
   - The server verifies the signatures and stores the invitation

3. **Acceptance**
   - The invitee's client requires its own certification of the inviter's signing key. When it has none, for example on the first invitation between the two or after the inviter replaced their keys, it asks for the inviter's account fingerprint and certifies the key first
   - It checks the invitation's grant and name signatures under that key, checks that the encrypted VEK is made out to its own account public key and that the key opens with its private key
   - It signs the grant with its own account signing key and sends that signature; the server stores the grant as signed by the member and adds the member to the vault's group
   - From the next sync on, the server includes the shared vault (its encrypted manifest and the member's grant) because the grant is active
   - Their client opens a shared vault only with a grant it signed itself: it checks the signature under its own signing key, derived from its private key, decrypts the VEK with its account private key, and with it the shared vault

4. **Revocation**
   - Removing a member from a shared vault, or leaving it, deletes their grant and their membership of the vault's group on the server. Deleting a shared vault deletes its group
   - The server no longer provides the shared vault or its email to the removed member, so their access is blocked. The vault keeps its VEK and Vault Delivery Keypair, so the remaining members are not affected

### 10.2. Access and keys
- **Group membership alone gives no access**: a group itself holds no keys. A user only gets access to a shared vault after being invited to it and accepting, which gives them their own grant.
- **Each key has one job**: the account encryption keypair only receives vault keys, and a Vault Delivery Keypair only decrypts email, so a key stored inside a vault never opens anything outside it.
- **Grants are tied to their vault**: a grant is encrypted under a label that names the vault, so it cannot be used for another vault.
- **Grants and keys are signed**: a grant carries an Ed25519 signature by the member who holds it, and a published account public key or delivery key one by the account that published it, each over a message that names its purpose, so a grant cannot be created by someone who merely knows a public key, and a signature made for one purpose does not verify for another. The server checks every signature on upload. A client opens a shared vault only with a grant signed by its own account, and encrypts a vault key only for a public key signed by a signing key its user certified ([10.3](#103-account-fingerprints-and-key-certifications)). A grant the server made up, signed with a key of its own, therefore never opens.
- **Own keys come from the private key**: a client uses the account public key the server serves as its own only after checking that it is the public half of the private key it holds, and derives its own signing public key from its signing private key. A server that serves another key as the user's own is refused.
- **Enforcement layers**: access to a vault's contents is enforced by cryptography (no grant, no key). Which vaults the server lists for a user, group membership and roles are enforced by the server. A few guards, such as refusing to delete the folder that represents a shared vault, are enforced only in the client.

### 10.3. Account fingerprints and key certifications
Every account has an account fingerprint, shown in the apps under Settings: the fingerprint of its account signing public key, 20 decimal digits in groups of four, taken from the SHA-256 of the key under a fixed label (`aliasvault/v1/signing-key-fingerprint`). The fingerprint is the same on every client, is not secret, and changes only when the signing key is replaced by a key rotation ([4.2](#42-key-rotation)). A user's own fingerprint is derived from their signing private key, decrypted with the Account Key, so it does not depend on the public key the server reports for the account.

The fingerprint is the one input the server does not control, so it has to be exchanged outside AliasVault: in person, by phone or over a channel the two people already trust. It is used in both directions, once per person:

- The inviter types the invitee's fingerprint to invite them. The server finds the account by the fingerprint and returns its signing key; the client refuses the key unless its fingerprint is the typed fingerprint.
- The invitee types the inviter's fingerprint to accept. The client checks the inviter's signing key the same way.

Each check ends in a *key certification*: an Ed25519 signature by the checking account over a message that names the certifier, the certified account and the certified signing key (label `aliasvault/v1/sig/key-certification`). The certifications are stored on the server and served back with the rosters of the groups the user administers, with the list of people the user verified, and with invitations. A client trusts a certification only after verifying it under its own signing public key, derived from its private key, so the server can withhold a certification but cannot forge one. Without a valid certification the client refuses to hand out or accept a vault key and asks for the other person's fingerprint; it never accepts a served key on its own.

The certified key anchors everything that follows: the account public key a vault key is encrypted to must be signed by it, and the invitation and grant signatures are checked under it. Later shared vaults between the same two people need no further fingerprint. Trust is set up between the admin and each member only: members do not certify each other, as only the admin hands out vault keys. A key rotation ([4.2](#42-key-rotation)) signs the rotating account's own certifications again with its new signing key, in the same transaction; the certifications others made of the old key no longer match, so the next invitation between them asks for the new fingerprint. Leaving or being removed from a shared vault keeps the certifications, so sharing again later needs no fingerprint.

Finding a signing key with a given 20-digit fingerprint takes on the order of 10<sup>20</sup> key generations.

## 11. Protecting keys on the device
AliasVault gives you offline access to your data: each device keeps an encrypted copy of your vault together with the encrypted key hierarchy, so once it has synced you can unlock your vault without the network. You can unlock with your master password or a quicker method such as biometrics or a PIN; each method protects a copy of your Account Key that is stored only on that device, and the keys below it are then opened from the encrypted key hierarchy.

<a href={useBaseUrl('/assets/diagrams/whitepaper/11-keys-on-the-device.html')} target="_blank" rel="noopener noreferrer" title="Open full screen">
  <ThemedImage
    alt="AliasVault keys on the device diagram"
    sources={{
      light: useBaseUrl('/assets/diagrams/whitepaper/11-keys-on-the-device-light.svg'),
      dark: useBaseUrl('/assets/diagrams/whitepaper/11-keys-on-the-device-dark.svg'),
    }}

- **Master password**: the unlock key is derived with Argon2id from the salt and settings cached on the device, the KEK is derived from it with HKDF-SHA256, and the KEK decrypts the Account Key (see [Key derivation and key hierarchy](#4-key-derivation-and-key-hierarchy)).
- **Biometrics (mobile)**: the Account Key is encrypted with a key held by the device's secure hardware. iOS uses a Keychain item with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and the `biometryCurrentSet` access control; Android uses an AndroidKeyStore AES-GCM key with `setUserAuthenticationRequired(true)`, `AUTH_BIOMETRIC_STRONG` and `setInvalidatedByBiometricEnrollment(true)`.
- **PIN (mobile and browser extension)**: the Account Key is encrypted with AES-256-GCM under a key derived from the PIN with Argon2id (random 16-byte salt, 64 MiB, 3 iterations). The PIN encryption and the attempt policy are implemented once in the Rust core; after 4 failed attempts the encrypted Account Key is deleted and PIN unlock is disabled. A PIN has at least 6 characters: digits only on mobile, any characters in the browser extension. The browser extension stores the result in the extension's local storage; the mobile apps encrypt it once more with a key from the iOS Keychain (this-device-only) or the Android Keystore.
- **Passkey quick unlock (web app)**: the Account Key is encrypted with a key obtained from a passkey's PRF extension and stored in the browser.

Locking the vault removes the decrypted vault and the Account Key from memory; the encrypted vault stays on the device, so the next unlock can work offline. Logging out instead removes all data from the device, including the encrypted vault and key hierarchy, so logging back in requires a connection to the server.

On Android, the app is excluded from system backups (`allowBackup="false"`), so the encrypted vault and the encrypted keys are not copied to cloud backups. On iOS the Keychain items are marked as this-device-only.

The salt and Argon2id settings are stored in the file's header, so the password alone is enough to open it again.

## 13. Known limitations
These are the known limitations of the current design relative to the [threat model](#2-threat-model), including trade-offs made on purpose. Each applies only to an attacker who already has what the table lists.

| | Limitation | Requires | Effect | Status |
|---|---|---|---|---|
| [13.1](#limitation-shared-member-removal) | Revocation from a shared vault is not cryptographic | Former membership of the vault and its newer ciphertext obtained outside the API | Read what was added to that vault after the removal | By design |
| [13.2](#limitation-rollback) | Vault freshness is not verified | Control of the server | Serve an older vault revision; no reading or changing of contents | By design |
| [13.3](#limitation-pin-unlock) | PIN unlock in the browser extension | A copy of the extension's storage (forensic access or a compromised device), for a user who turned PIN unlock on | Guess the PIN offline | Opt-in, off by default |
| [13.4](#limitation-post-quantum) | RSA-2048 for public-key encryption | Stored ciphertext and a quantum computer able to break RSA-2048 | Decrypt shared vault keys, emails and Login with Mobile transfers | Post-quantum scheme planned |
| [13.5](#limitation-argon2-parameters) | Argon2id floor on a new device | Control of the server while the user logs in on a new device | Guess the master password offline at the OWASP minimum cost | Floor raised after migration |

1. <Link id="limitation-shared-member-removal" />**Revocation from a shared vault is not cryptographic.** The server stops serving the vault and its email to a removed member, and their client deletes its local copy. The VEK and Vault Delivery Keypair stay the same, so the remaining members are not affected. Reading content added after the removal requires both the keys the former member kept and ciphertext the server no longer serves them, such as from a leaked copy of the server database. The remediation is to change the passwords in the shared vault where needed: the former member synced those items before the removal, and no change of keys can take that back. To also keep anything added later out of reach of the former member, create a new shared vault, move the items and aliases to it, invite the remaining members and delete the old vault, which deletes its data from the server, including its emails.
2. <Link id="limitation-rollback" />**Clients verify that a vault revision is authentic, not that it is the latest.** The server can serve a revision that members of the vault wrote earlier, or an empty vault, as the current one; it cannot read, change or create vault contents ([2.4](#24-what-the-server-knows-and-can-do)). A client accepts such a revision, so changes made after it are lost and older states of items return. Clients accept older revisions on purpose: a server restored from a backup serves them in the same way, and refusing them would lock users out of their vaults.
3. <Link id="limitation-pin-unlock" />**PIN unlock in the browser extension is an opt-in convenience.** PIN unlock is off by default and the master password is the default unlock method; the PIN setting notes that a PIN can be less secure than the master password. The Account Key is encrypted under a key derived from the PIN with Argon2id, and the extension deletes it after 4 failed attempts. This limitation applies only to an attacker who already has a copy of the extension's storage from the user's browser profile, which takes forensic access to the device or a compromised device, both outside the threat model ([2.5](#25-out-of-scope)). Such an attacker is not bound by the attempt limit and can try PINs offline at the cost of one Argon2id derivation per guess, which is feasible for a 6-digit PIN; a longer PIN with letters and symbols takes more guesses. Browsers give extensions no hardware-bound key storage, so the extension cannot bind the PIN-encrypted key to the device. On mobile, the PIN-encrypted Account Key is also encrypted with a device-bound key from the iOS Keychain or the Android Keystore, so a copy of the app's storage alone is not enough to start guessing.
4. <Link id="limitation-post-quantum" />**Public-key encryption uses RSA-2048; a post-quantum algorithm is planned.** Grants, email keys and Login with Mobile use RSA-2048-OAEP. An attacker who keeps a copy of that ciphertext (from the server database or captured traffic) could decrypt it once a quantum computer able to break RSA-2048 exists, and with it the shared vault keys, emails and Account Keys it protects. RSA-2048 provides 112-bit security, which NIST SP 800-57 Part 1 approves through 2030; the NIST draft transition plan (IR 8547) sets 2035 for moving public-key encryption to post-quantum algorithms. Vault contents and the keys that protect the personal vault at rest use AES-256-GCM, which is considered safe against quantum computers. Every RSA ciphertext carries an algorithm identifier, so a post-quantum scheme can be added next to RSA without breaking existing data; it will be added once well-reviewed implementations exist on every platform AliasVault supports.
5. <Link id="limitation-argon2-parameters" />**A new device accepts Argon2id settings down to the OWASP minimum.** Accounts use 64 MiB and 5 iterations, but a device that has never logged in before does not know that, so it accepts any settings down to the OWASP minimum of 19 MiB and 2 iterations ([section 4](#4-key-derivation-and-key-hierarchy)). A malicious server could send that minimum to a new device and obtain one login proof to guess the master password against at the lower cost. A device that logged in before refuses weaker settings than it used, and a leaked database only allows guessing at the account's own settings. The minimum matches the default for accounts until version 0.31.0; once all accounts have migrated to the current defaults, it will be raised to match them.

## 14. Security assurance and disclosure

- **Open source.** The server, every client and the Rust core are developed in one public repository under the AGPL-3.0 license. The browser extensions and the Android app (via F-Droid) are built from that source; the releases on GitHub are tagged.
- **Independent review.** AliasVault runs a public responsible disclosure program and has received and fixed reports from independent researchers since 2025; the advisories are published as [GitHub security advisories](https://github.com/aliasvault/aliasvault/security/advisories) and the reporters are credited on the [responsible disclosure page](https://www.aliasvault.com/responsible-disclosure). As of October 2026, preparations for an independent security audit of the cryptographic design and the Rust core are in progress; the report and our response will be published on this page once the audit is complete, expected before the end of January 2027.
- **Reporting a vulnerability.** Email security@aliasvault.com. [SECURITY.md](https://github.com/aliasvault/aliasvault/blob/main/SECURITY.md) states what to include, how reports are classified against the threat model of this document, when a CVE is requested, and the disclosure timeline; a machine-readable [security.txt](https://github.com/aliasvault/aliasvault/blob/main/SECURITY.txt) points to the same policy.
- **Supported versions.** Security fixes are applied to the latest release only.

## Appendix B. Glossary

| Term | Meaning |
|---|---|
| **Unlock key** | The Argon2id output of the master password. Never used directly. |
| **KEK** | Key Encryption Key: derived from the unlock key with HKDF, decrypts the Account Key. |
| **Account Key (AK)** | Random key that opens everything the account owns: the personal VEK and the account private keys. |
| **VEK** | Vault Encryption Key: random key of one vault, personal or shared. |
| **Manifest** | The encrypted document on the server that holds one vault's items. |
| **Data bucket** | A separately encrypted part of a vault for data that changes often. |
| **Blob** | The encrypted bytes of one attachment or logo, with its own key. |
| **Grant** | A vault's VEK encrypted for one member's account public key, signed by the member who holds it. |
| **Vault Delivery Keypair** | The RSA keypair of a vault that incoming email is encrypted to. |
| **Email claim** | The server-side record that an alias address belongs to a vault. |
| **Group** | A set of accounts that can hold shared vaults; a group holds no keys. |
| **Account fingerprint** | 20 digits derived from an account's signing public key, compared outside AliasVault before sharing. |
| **Key certification** | An account's signature stating that a signing public key belongs to another account, made after checking its fingerprint. |
| **Account unlock method** | A server-stored copy of the Account Key under a KEK; today the master password. |
| **Device unlock method** | A device-only copy of the Account Key protected by biometrics, a PIN or a passkey. |
